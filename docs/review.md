# レビュー観点

機械的検証でない一般レビュー項目．

## 範囲

- PR の変更が閉じる Issue と対応しているか
- 新しいファイルが `mod` 宣言から辿られているか
  - CIが機能しない

## 仕様

- Issue の仕様の各項目を満たしているか
- エラーのバリアントが仕様の意図した場面で返るか

## テスト

- 条件を1つ壊してもテストが全部通る分岐がないか
  - CI の mutants ジョブが PR の差分について調べる．手元では `git diff origin/main... > pr.diff` のあと `cargo mutants --in-diff pr.diff`
- 失敗する場合だけでなく成功する場合もテストしているか
- 失敗したとき状態が変わっていないことを確かめているか
- エラーは種類だけでなく保持する値も確かめているか
- 次のテストを書いていないか
  - 定数や定数に準ずるもの．定数を変えるのは意図した変更なので，テストも直すだけになる
  - 検証しないことのテスト
  - 他のテストと実質的に重複するもの
- 要素が1つのリストから検索するような弱いテストにしていないか

## 正しさ

- 外部コマンド (git) に利用者由来の文字列を渡すとき，前に `--end-of-options` を置く．`-` で始まる文字列がオプションとして解釈される
- git のメッセージの文言で状態を判定しない．翻訳や版で変わるので終了コードで判定する
- 出力が利用者の git 設定に左右されないようにする (`--no-color`，`--no-ext-diff`，`--no-renames`)
- 型の最大値を渡したときに外部コマンドや変換が失敗しないか (`usize::MAX` を `git log -n` に渡すなど)

## 設計

- 既存の関数と同じ処理を書き直していないか (DRY)
  - 見つけたら既存の関数名を挙げる
- 構造体のフィールドを `pub` にしていないか
  - 取得メソッドは `get_hoge` ではなく `hoge`
- 同じリポジトリの他の公開型と derive を揃える (`Debug, Clone, PartialEq, Eq` など)
- 無意味にメモリ確保しない
  - `&str` で足りるところで `to_string()` しない
- 異常系は早期 return や `let-else` で抜ける

## 名前

- 中身と食い違う名前にしない  
  - 例
    - `&Path` を返す `get_pathbuf`
    - 整数の添字を入れる `delete_item`
- テスト名は実際に呼んでいる関数に合わせる

## ドキュメントコメント

- 1行目は要約．続きがあれば空行を挟む
- 宣言でないものにつけない
  - ok
    - 変数
    - 関数
    - トレイト
- 型を見ればわかることは書かない
- モジュールの先頭に `//!` を書く

## コメント

- 見ればわかることは書かない

## エラー

- バリアントが持つ値をメッセージに出す (`"品目 {0:?} が見つかりません"`)
- 呼び出し側が区別すべき2つの失敗を同じバリアントで返さない
- エラーメッセージに出すコマンドは，実際に実行したものにする
